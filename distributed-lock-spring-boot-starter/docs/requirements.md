# 需求

## 背景

需要一套声明式分布式锁组件，供业务方法以注解方式获得互斥能力，避免手写 `tryLock/unlock` 模板代码。

## 用户与场景

- 使用方：同一套代码库下的多个业务服务（Spring Boot 3.x + JDK21）。
- 典型场景：防重复提交、按资源 ID 串行化操作、按用户维度互斥、读写分离的共享资源。

## 成功标准

1. 业务方在方法上标注 `@DistributedLock` 即可获得分布式互斥，无需手写锁代码。
2. 配置了 Redis（容器中存在 `RedissonClient`）时组件自动生效；未配置 Redis 时组件完全不装配，对业务零影响。
3. 锁 key 支持 SpEL，能按方法参数动态生成。
4. 支持多种锁类型：可重入、公平、读、写、多 key 联锁。
5. 支持配置等待时间与持有时间；持有时间默认走看门狗自动续期，防止业务未完成锁提前释放。
6. 获取锁失败时有明确策略（抛异常 / 返回 null / 兜底方法）。
7. 与 Spring 事务共存时，锁在事务之外（先锁后事务、先提交后放锁），避免并发脏数据。

## 边界 / 不做

- **不做限流**。限流属于另一类问题（流量整形），与互斥锁语义不同；如需限流使用 Sentinel（每实例自我保护）或 Redisson `RRateLimiter`（集群共享配额），不纳入本组件。详见 [decisions.md](decisions.md)。
- **不做库存扣减**。秒杀等场景的库存原子扣减属业务核心逻辑（Lua/分布式锁由业务自管），不在通用 starter 职责内。
- **不自带 RedissonClient 创建**。本 starter 只消费 `RedissonClient` Bean，由使用方（如 `redisson-spring-boot-starter`）提供。
- **不处理 self-invocation**。同类内部方法互调不触发 AOP，这是 Spring AOP 通用限制，文档说明而非框架绕开。
